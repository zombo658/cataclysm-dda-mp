# Заметки по архитектуре 0.I-1 (этап 1)

Только чтение кода, ничего не менялось. Номера строк — по снимку 0.I-1.

## 1. Как `do_turn()` раздаёт ходы

Файл `src/do_turn.cpp`. Один вызов `do_turn()` = один ход игры (1 секунда,
`calendar::turn += 1_turns`, стр. 475). Порядок внутри хода:

1. Глобальная обработка: таймеры, миссии, погода, орды, автосейв, свет.
2. `u.activity.do_turn( u )`, пока у аватара есть очки ходов и активность
   (долгое действие тратит ходы аватара без ввода).
3. Звуки NPC и аватара → маркеры.
4. **Ввод аватара** (стр. ~564–605). Пока `u.get_moves() > 0`:
   `g->handle_action()` блокирующе ждёт клавишу и выполняет действие. Действие
   уменьшает `moves`. Цикл крутится, пока ходы не кончатся. Если аватар спит или
   занят долгим действием, ветка `else`: опрос клавиатуры раз в 100 мс без
   блокировки.
5. Карта: падение, транспорт, поля, предметы, взрывы, `sounds::process_sounds()`,
   `m.build_map_cache()`.
6. **`monmove()`** (стр. 267) — монстры, потом NPC (см. ниже).
7. `overmap_npc_move()` — NPC вне пузыря путешествуют по глобальной карте.
8. **`u.process_turn()`** — здесь аватару начисляются ходы на следующий тик.
9. Обновление тела, морали (раз в минуту и для NPC), звуковые эффекты.

### Откуда берутся очки ходов

`Character::process_turn()` (`src/character.cpp:2418`): эффекты, урон со
временем, предметы, `suffer()`, `recalc_speed_bonus()`, затем
`moves += get_speed()` (обычно +100 за ход). `npc::process_turn()`
(`src/npc.cpp:3356`) вызывает его и добавляет мелочи (стамина, доверие).
Монстры — `Creature::process_turn()`, там же `moves += get_speed()`.

Действие стоит очков: шаг ~100 (зависит от местности), атака — по оружию и
т. д. Существо действует, пока `moves > 0`; быстрое может сделать несколько
действий за ход, медленное копит долг (`moves < 0`).

### NPC внутри `monmove()` (стр. 357–400)

```
for( npc &guy : g->all_npcs() ) {
    guy.process_turn();                    // +ходы (если нет effect_npc_suspend)
    while( !dead && !спит && moves > 0 && turns < 10 ) {
        guy.move();                        // одно решение ИИ
        if( moves не изменились ) счётчик холостых итераций++;
    }
    if( turns == 10 ) { "%s faints!"; guy.reboot(); }
}
```

Важно для RC-NPC:

* Ходы NPC начисляются **в начале** его обработки в `monmove()`, а тратятся
  сразу в том же цикле. Аватар же получает ходы в конце хода и тратит их в
  начале следующего. Внутри одного `do_turn()` порядок такой: аватар →
  монстры → NPC.
* Если `npc::move()` 10 раз подряд не потратил ходов, вылезает `debugmsg`
  «entered infinite loop» и NPC «падает в обморок» (`npc::reboot()`). Значит,
  пауза для RC-NPC не может быть реализована как «вернуться из `move()`, не
  потратив ходы». Варианты: ждать команду внутри `move()` (блокирующе, с
  перерисовкой и опросом сети), или пропускать NPC в этом цикле, оставляя ему
  ходы, и не давать `do_turn()` продвинуть время.
* Спящий NPC (`in_sleep_state()`) в цикл вообще не входит.

## 2. `npc::move()` и `npc::execute_action()`

`src/npcmove.cpp:1334`. Каждый вызов принимает одно решение:

1. Обновление отношения (бегство), `regen_ai_cache()` — оценка опасности, цели.
2. Операция/заклинание → `npc_player_activity`.
3. Опасное поле рядом → шаг в сторону, `return`.
4. Цепочка приоритетов → `npc_action`: взрывчатка, бегство, лечение астмы,
   атака цели, проверка звука, иначе `address_needs()` (еда, сон, лечение),
   `address_player()` (разговор, следование), охрана поста, следование за
   игроком, активность (`NPCATT_ACTIVITY`), работа в лагере, поиск предметов,
   долгосрочная цель.
5. `execute_action( action )` (стр. 1608) — большой `switch` по `npc_action`,
   каждая ветка вызывает примитив: `move_to()`, `move_to_next()`,
   `move_pause()`, `do_reload()`, `pick_up_item()`, `do_player_activity()`,
   атаки через `ai_cache.current_attack->use()` и т. д.

Если в конце `execute_action()` ходы не изменились, пишется только отладочное
сообщение. `npc_noop` выходит сразу. `npc_undecided` → `complain()` +
`move_pause()`.

Полезные примитивы для команд RC-NPC:

* `npc::move_to( tripoint_bub_ms, no_bashing, nomove )` (стр. 2949) — шаг на
  соседнюю клетку. При враждебном существе на клетке бьёт его
  (`melee_attack`), открывает двери, обходит союзников. То есть «шаг» и
  «атака соседней клетки» по сути один примитив, как у аватара.
* `npc::move_pause()` (стр. 3438) → `Character::pause()`: тратит ход, раз в
  час может переключить оружие (это надо будет отключить для RC-NPC).
* `npc::pick_up_item()` / `find_item()` — подбор работает через
  `wanted_item_pos`; для «подобрать всё» скорее нужен свой код поверх
  `Character::pick_up` или `pickup_activity_actor`.
* Плавание: `Character::move` вызывает `avatar_action::swim` только для
  `!is_npc()` (`src/character.cpp:12973`, «TODO: NPCs can't swim!»).

**Место хука**: в начале `npc::move()` (после проверки на смерть) —
`if( mp::is_remote( *this ) ) { mp::rc_npc_move( *this ); return; }`.
Так весь ИИ, включая `act_on_danger_assessment()` и следование, обходится.

## 3. `control_npc_menu()` — смена управления

`src/debug_menu.cpp:1927` → `avatar::control_npc_menu()`
(`src/avatar.cpp:191`) → `avatar::control_npc( npc & )` (стр. 156).

Работает только для союзников (`is_player_ally()`). Что делается:

1. Обновить цели миссий: всё, что ссылалось на ID аватара, перевести на ID NPC.
2. Три обмена через «теневого NPC» `get_shadow_npc()`:
   `swap_character()` копирует всё содержимое `Character` (тело, инвентарь,
   навыки, ID...), `std::swap` меняет NPC-объекты. В итоге объект `avatar`
   остаётся тем же (синглтон), но внутри у него данные NPC, а бывший аватар
   становится NPC-последователем.
3. Обновить список последователей, фракцию, кэш освещения, перецентрировать
   карту (`g->update_map`), отправить событие `game_avatar_new`.

Вывод: штатный механизм — это **подмена данных**, а не два управляемых
персонажа. Для RC-NPC он не подходит как основа, но показывает, что вся
симуляция завязана на один объект `avatar`, а пузырь реальности едет за ним
(`update_map`). Для отладки RC-NPC можно временно забрать управление этим
пунктом и вернуть обратно.

## 4. Где код предполагает одного игрока

`get_avatar()` / `get_player_character()` — около 1130 вызовов в 134 файлах
`src/*.cpp`. Большая часть — UI (меню, инвентарь, карта, отрисовка), их RC-NPC
не затрагивает. Ниже то, что влияет на симуляцию вокруг RC-NPC.

### Монстры

* `monster::plan()` (`src/monmove.cpp:484`) сначала смотрит на аватара как на
  цель, потом перебирает NPC (стр. 531). NPC в целях монстров уже есть,
  RC-NPC будут атаковать — хорошо.
* `monster.cpp:3408, 3419` — простуда/грипп заражают только аватара
  («No NPCs for now»).
* `monmove.cpp:236` — завершение пути монстра сравнивается с позицией аватара.
* `do_turn.cpp:333` — тревога о приближении (motion alarm) только для аватара.

### Карта, видимость, пузырь

* Пузырь реальности (`map`) центрирован на аватаре; `g->update_map( u )`
  сдвигает его. RC-NPC за пределами бубла выгружается в `overmap_buffer`.
* `map::build_map_cache()` / кэш видимости (`seen_cache`) считаются от
  аватара (`map.cpp:7289` использует режимы зрения аватара). Для поля зрения
  RC-NPC на этапе 4 нужен отдельный расчёт (у NPC есть `Character::sees()`,
  но он дорог на всю область).
* Память карты (`get_memorized_tile`) есть только у `avatar`.
* Звуки: маркеры звуков обрабатываются для аватара и для NPC в
  `MAX_VIEW_DISTANCE` от аватара (`do_turn.cpp:550, 572`).

### Персонаж

* `Character::is_avatar()` / `is_npc()` развилки в действиях: вопросы
  `query_yn`, выбор предметов, подтверждения — для NPC идут по
  автоматическому пути или пропускаются. Для меню на этапе 5 это главная
  сложность: интерактив придётся выносить в протокол.
* Сообщения: `add_msg_if_player()` у NPC не выводится, `add_msg_if_npc()` /
  `add_msg_player_or_npc()` выводятся хосту в третьем лице. Для лога второго
  игрока нужен перехват.
* `npc::is_player_ally()`, `is_walking_with()`, `guaranteed_hostile()` —
  отношения считаются к аватару. RC-NPC должен быть союзником аватара
  (фракция `your_followers`), иначе его атакуют союзники хоста и наоборот.
* `npc.cpp:3505` — правило `hold_the_line` смотрит на аватара.
* `character.cpp:12973` — NPC не умеют плавать.

### Время и долгие действия

* Сон/долгое действие аватара: ветка `else` в `do_turn()`, мир идёт без ввода.
  Если в этот момент RC-NPC ждёт команду, мир должен остановиться — нужно
  решение из «Открытых вопросов».
* У NPC долгие действия идут через `npc_player_activity` →
  `do_player_activity()`.

## 5. Что из этого следует для этапа 2

   `npc::move()`.

   видит «холостых» вызовов и `reboot()` не срабатывает. Минус: хост не может
