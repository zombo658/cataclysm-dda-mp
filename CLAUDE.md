# CDDA Multiplayer — форк Cataclysm: Dark Days Ahead

Этот файл — рабочая память проекта. Читай его в начале каждой сессии. Обновляй разделы «Статус» и «Журнал решений» после каждого завершённого шага.

## Цель

Кооператив на двоих (потом, возможно, больше) в оригинальной CDDA. Хост играет обычным аватаром, второй игрок подключается по сети и управляет своим персонажем.

## Базовая версия

* Снимок исходников стабильного тега `0.I-1` (апстрим CleverRaven/Cataclysm-DDA, коммит `7b2efa5cea38e4d4d97dd0e63b28b9148623da59`), не master/experimental.
* Апстрим не догоняем. Переход на новую стабильную версию — отдельное решение.
* Репозиторий: `zombo658/cataclysm-dda-mp`. История апстрима не импортирована. Сравнить с оригиналом:
  `git fetch --depth 1 https://github.com/CleverRaven/Cataclysm-DDA.git tag 0.I-1` и `git diff 0.I-1 HEAD`.

## Архитектура (принятое решение)

Второй игрок — это NPC, у которого вместо ИИ очередь команд из сети.

* Аватар и NPC наследуются от `Character`, поэтому у NPC уже есть всё: инвентарь, здоровье, навыки, сохранение, участие в цикле ходов.
* Вводим «удалённо управляемого NPC» (remote-controlled NPC, далее RC-NPC). Когда у RC-NPC есть очки ходов, он берёт команду из очереди вместо ИИ.
* ~~Если у RC-NPC есть ходы, а очередь пуста, мир ставится на паузу и ждёт.~~ Заменено решением владельца: время второго игрока не считается, его команды выполняются мгновенно, мир его не ждёт (пошаговая пауза осталась только для hot-seat без сервера).
* Сервер авторитарный: вся симуляция идёт только в процессе хоста.
* Пузырь реальности остаётся центрированным на аватаре хоста. На первых этапах RC-NPC запрещено уходить за его пределы.
* Сетевой протокол: TCP, JSON по одному объекту на строку (NDJSON), порт 7777.
* ~~Клиент второго игрока пишется на Python, отдельно от игры.~~ Клиент — сама игра (Multiplayer → Join game); Python-клиент оставлен для отладки.
* Механики второму игроку добавляются по одной (тонкий клиент), а не стримом экрана хоста — решение владельца.

Подробный разбор кода — `docs/mp/architecture-notes.md`.

## Правила работы

1. Маленькие шаги. Одна задача — один рабочий результат — один коммит.
2. Минимум изменений в ядре. Новый код кладём в `src/mp/`. В существующие файлы добавляем только тонкие хуки (вызов функции из `src/mp/`), чтобы патч оставался читаемым и его можно было перенести на другую версию.
3. Не трогаем JSON-контент в `data/` без явной необходимости.
4. Сначала понять, потом менять. Прежде чем править чужой код, прочитай, кто ещё его вызывает. Если фикс — костыль, так и скажи.
5. Всё должно собираться перед коммитом. Сломанную сборку не коммитим.
6. Пишем в стиле проекта (см. `.astylerc`, `doc/` по стилю кода).
7. Если решение по дизайну неочевидно — не выбирай сам молча, предложи варианты и спроси.

## Сборка

### Windows (основная платформа владельца)

Сборку делает GitHub Actions: `.github/workflows/mp-windows.yml` (MSVC + vcpkg, как апстримный релиз 0.I).
Запускается на пуш в `mp` и `claude/**` при изменениях в `src/`, `data/`, `msvc-full-features/`, `tools/mp/`, или вручную (Run workflow).
Результат — артефакт `cdda-mp-windows-x64` (zip ~200 МБ: игра с графикой и переводами + папка `mp` с клиентом и докой), хранится 14 дней. Идёт ~35 минут. Первая успешная сборка — run 4 (коммит `df71eb1`).
Инструкция для игроков — `docs/mp/how-to-play.md`.

**Имена файлов в `src/mp/` не должны совпадать с файлами в `src/`**: MSVC кладёт все `.obj` проекта в одну папку по имени файла, и один объект затирает другой (так сломалась сборка с `src/mp/main_menu.cpp`). Workflow проверяет это первым шагом.

Новые `.cpp` в `src/mp/` MSVC-проект подхватывает сам (`msvc-full-features/Cataclysm-lib-vcpkg-static.vcxproj`, маска `..\src\mp\*.cpp`).
Проверить, что код компилируется под Windows, можно здесь же: `apt-get install g++-mingw-w64-x86-64` и
`x86_64-w64-mingw32-g++-posix <флаги из сборки без -D_XOPEN_SOURCE=600> -fsyntax-only src/mp/<файл>.cpp`.

### Linux (разработка в облачном контейнере)

Отладочная curses-сборка (проверено в облачном контейнере, Ubuntu, g++, 4 ядра). Нужны `g++`, `make`, `libncurses-dev`.

```
make -j$(nproc) RELEASE=0 TILES=0 SOUND=0 LOCALIZE=0 ASTYLE=0 LINTJSON=0 BACKTRACE=0 cataclysm
```

* Полная сборка — около 13–15 минут на 4 ядрах. Пересборка после правки одного `.cpp` — около минуты.
* Файлы `src/mp/*.cpp` Makefile подхватит, только если добавить каталог в его список исходников — сделать при первом файле в `src/mp/`.
* Сборка с `-Werror`: любое предупреждение ломает её.

Запуск (игре нужна UTF-8 локаль):

```
LANG=C.UTF-8 LC_ALL=C.UTF-8 ./cataclysm --userdir ../cdda-userdir/
```

Проверка без экрана: запустить в `tmux new-session -d -x 200 -y 60`, слать клавиши `tmux send-keys`, смотреть `tmux capture-pane -p`.

Форматирование: в контейнере нет `astyle`. Если появится — `astyle --options=.astylerc` на изменённых файлах перед коммитом.

#### Как это устроено и как проверить

Код — `src/mp/rc_npc.{h,cpp}`. Хуки в ядре (по одной-две строки):
`npc::move()` (`src/npcmove.cpp`), условие цикла NPC в `monmove()` и начало `do_turn()` (`src/do_turn.cpp`),
`game::handle_action()` перед `gamemode->pre_action()` (`src/handle_action.cpp`),
`npc::store/load` (`src/savegame_json.cpp`), пункт debug-меню (`src/debug_menu.{h,cpp}`).

Проверка вручную:
1. В `<userdir>/config/keybindings.json` привязать debug-меню к обратной кавычке (без привязки игра показывает только «Info…»):
   ```
   [{"type":"keybinding","id":"debug","category":"DEFAULTMODE","bindings":[{"input_method":"keyboard_char","key":"`"}]}]
   ```
2. Новая игра «Play Now! (Default Scenario)» — в убежище есть NPC.
3. Обратная кавычка → `p` Player… → `X` Multiplayer: remote NPC → `t` → выбрать NPC. Он становится последователем с флагом.
4. После хода хоста появляется «Waiting for <имя> to act…». Клавиши движения, `.` и `g` теперь управляют NPC; действия хоста, тратящие время, запрещены. Время идёт на 1 секунду после хода NPC и хода хоста.
5. Debug-меню → `q` ставит команду в очередь вручную (так же будут приходить команды из сети).

#### Известные ограничения (этап 2)

* Атака командой проверена только компиляцией: в тесте не было монстров.
* `npc::move_to()` сам уводит NPC с опасного поля (огонь и т. п.) на соседнюю клетку — для игрока это неожиданно.
* Выход за пузырь реальности просто запрещён (команда отклоняется) — ждёт решения из «Открытых вопросов».
* Хост может через диалог дать RC-NPC поручение (активность) — оно выполнится, отменить его второй игрок пока не может.
* Сообщения действий NPC местами во втором лице («You pick up: 1 file») и уходят в лог хоста; плюс лишнее «completed the assigned task». Лог второго игрока — этап 4.
* «Waiting for … to act…» пишется в лог каждый ход.
* При включении флага сгенерированный NPC убежища становится последователем, и игра пишет «Mission "Faction succession" is failed» — побочный эффект смены фракции, не разбирался.

### Этап 3. Сеть (первый играбельный кооп)

* [x] TCP-сервер в процессе игры, неблокирующий, опрашивается из цикла хода.
* [x] Команды из сети → очередь RC-NPC.
* [x] Простой клиент на Python: читает клавиши, шлёт команды. Картинку второй игрок пока смотрит через tmux/Parsec с экрана хоста.
* [x] Минимальный ответ сервера: ок/ошибка, статус персонажа (HP, голод и т. п.).

#### Как это устроено и как проверить

Код: `src/mp/net_server.{h,cpp}` (сокеты, без знания об игре), `src/mp/protocol.{h,cpp}` (JSON ↔ команды),
клиент `tools/mp/client.py`. Протокол — `docs/mp/protocol.md`.
Сеть опрашивается в `mp::wait_for_remote_players()` (начало каждого хода) и, пока мир ждёт второго игрока,
каждые 125 мс из цикла ввода хоста: хук `mp::host_input_should_yield()` в `game::get_player_input()` прерывает ожидание клавиши.

1. Хост: debug-меню → Player… → Multiplayer: remote NPC → `t` (выбрать NPC), затем `s` (запустить сервер на 7777).
2. Второй игрок: `python3 tools/mp/client.py --host <IP хоста>`. Клавиши `hjklyubn`/стрелки/цифры — шаг, `a`+направление — атака, `.` — ждать, `g` — подобрать, `s` — статус, `q` — выход.
3. Для автотестов: `python3 tools/mp/client.py --script "move w" wait status` печатает все ответы сервера.

#### Известные ограничения (этап 3)

* Windows: сервер на Winsock проверен кросс-компиляцией MinGW и эхо-сервером под Wine; в самой игре под Windows не запускался — проверяет владелец по сборке из Actions.
* Сервер запускается вручную из debug-меню при каждой загрузке, не сохраняется.
* Один клиент и один RC-NPC: команды идут первому RC-NPC в пузыре.
* Без клиента RC-NPC стоит и пропускает ходы (временный ответ на вопрос про отключение).
* Атака командой по-прежнему не проверена на живом монстре.

#### Как это устроено

* Вкладка **Multiplayer** в стартовом меню (`src/main_menu.cpp`, правки в 5 местах; пункты и выбор мира — `src/mp/menu_tab.cpp`).
* **Host game**: выбор мира → обычная загрузка сохранения → `mp::request_host()`; на первом ходу `mp::wait_for_remote_players()` запускает сервер и, если RC-NPC нет, спрашивает, кем играет второй игрок (NPC рядом или новый случайный, `spawn_partner()`).
* **Join game**: `src/mp/client_ui.cpp` — ввод адреса, подключение с таймаутом 5 с, свой экран (статус, карта, лог), мир не загружается.
* Сервер шлёт `log`, `view` и `your_turn` каждый раз, когда ждёт второго игрока (`src/mp/view.cpp` — что видит RC-NPC: `npc::sees()` по клеткам радиуса 25).
* Сеть: `src/mp/net.{h,cpp}` — сервер и клиент на общей логике соединения. Сеть опрашивается и во время хода хоста (хук в `game::get_player_input()` каждые 125 мс), иначе клиент не получал бы ответа, пока хост думает.

#### Известные ограничения (этап 4)

* Карта у клиента символами, без тайлов; широкие символы (CJK) не учитываются.
* Карта у клиента обновляется только на его ходу.
* Сервер не останавливается при выходе хоста в главное меню (до закрытия игры).
* Host game работает только с уже созданным миром и персонажем.

* [x] Двери, окна, взаимодействие с клеткой: открыть/закрыть/разбить/осмотреть (`src/mp/world_actions.cpp`, копии функций хоста для `npc`). Части `iexamine`, рассчитанные на аватара (например «подсмотреть сквозь занавески»), могут действовать за аватара хоста — не проверено.
* [x] Крафт: окно как у хоста (`src/mp/remote_crafting.cpp` — копия `select_crafter_and_crafting_recipe()`), всё, что зависит от персонажа, считает хост тем же кодом (`mp::craft_screen`, обёртки в конце `src/crafting_gui.cpp`). Крафт выполняется мгновенно. Нет пока: вложенных групп рецептов, практики, «похожих», сравнения, выбора крафтера, отметок «прочитано»; компоненты выбирает хост, как для NPC.

Сон и ожидание идут в реальном времени хоста (не мгновенно).

## Открытые вопросы (решает владелец проекта)

* Долгие действия (крафт, чтение, сон) одного игрока проматывают время для всех. Прерывать? Спрашивать второго игрока? Запрещать, пока второй активен?
* Смерть хоста / смерть второго игрока — что происходит?
* Что делать, если RC-NPC пытается выйти за пузырь реальности?
* Отключение клиента посреди игры: пауза, ИИ берёт управление, персонаж стоит? (Сейчас: стоит.)
* Мгновенные действия второго игрока очень сильны (может убежать от любого монстра, доигрывает подбор мгновенно). Нужны ли ограничения — например, мгновенный режим только вне боя?

## Статус

Этапы 0–4.5 закончены, этап 5 почти весь. Клиент второго игрока — «зеркало»: хост шлёт копии персонажа, карты вокруг, существ, погоды и оверкарты, и клиент показывает **настоящий экран игры** (та же отрисовка с тайлами, освещением и одеждой на спрайтах, боковая панель, лог) и открывает настоящие окна игры (инвентарь, крафт, строительство, AIM, прицеливание, подбор, лист персонажа, бионики…). Действия выполняет хост: часть — нашими командами для `npc`, часть — пересылкой активности, которую код хоста назначил копии, вопросы игры (меню мебели, диалоги) задаются второму игроку. Время второго игрока не считается (кроме сна/ожидания). Вождение есть (хук в `vehicle::player_is_driving_this_veh()`), проверено только в здании. Не сделано: `veh_interact` (переделка машин), сортировка брони, тяга/волочение, зоны, торговля (не проверена), переназначение букв и настройки карманов.

Работа идёт в ветке `claude/dazzling-rubin-drix1n` (так требует облачная сессия). Ветку `mp` можно сделать из неё при слиянии.

## Журнал решений

* Выбран форк оригинала, а не переписывание с нуля.
* Второй игрок реализуется как NPC с сетевой очередью команд.
* База — стабильный тег `0.I-1`.
* Отдельный репозиторий `zombo658/cataclysm-dda-mp`; снимок исходников одним коммитом без истории апстрима (полная история весит несколько ГБ, апстрим не догоняем).
* Флаг RC хранится в JSON NPC (`"mp_remote"`), внутри — `std::set<character_id>` в `src/mp/`, чтобы не трогать `npc.h`.
* Пауза: RC-NPC без команд пропускается в `monmove()` с сохранением ходов; в начале следующего `do_turn()` время не идёт, пока он их не потратит. Хост в ожидании может только действия без затрат времени (список — `can_action_change_worldstate()` в `src/action.cpp`).
* Ввод хоста в ожидании передаётся лямбдой из `do_turn()`, чтобы не править `game.h` (иначе пересборка почти всего проекта).
* Команды очереди не сохраняются; после загрузки очередь пуста.
* Сеть: сервер и протокол разделены (`net_server` ничего не знает об игре). Ввод хоста во время ожидания прерывается хуком в `game::get_player_input()`, если пришло что-то из сети.
* Хост играет на Windows. Сеть написана с прослойкой POSIX/Winsock в `net_server.cpp`; готовую Windows-сборку делает GitHub Actions (MSVC, как апстрим), а не сам владелец.
* Кнопки: «Создать хост» и «Присоединиться» — вкладка Multiplayer в стартовом меню (решение владельца). Второй игрок играет из самой игры, а не из Python-клиента; Python-клиент оставлен для отладки.
* Клиент на Python без внешних зависимостей: на Windows без `windows-curses` работает простой консольный режим через `msvcrt`.
* Время второго игрока не считается (решение владельца): при запущенном сервере его команды выполняются сразу по приходу (из `protocol::poll()`, в т.ч. посреди ввода хоста), ходы выдаются на каждый шаг и обнуляются после; мир его не ждёт. Пошаговая пауза осталась для hot-seat без сервера.
* Если сервер запущен, а клиента нет, RC-NPC пропускает ходы и игра идёт (временно, пока не решён вопрос об отключении клиента). Если сервер не запущен — hot-seat.
* Тайлы у клиента рисует тот же `cata_tiles`, что и игра: новый метод `draw_remote_view()` (объявление — одна строка в `cata_tiles.h`, тело в `src/mp/remote_tiles.cpp`). Клетки рисуются на z = -OVERMAP_DEPTH, чтобы запасной путь отрисовки не лез в незагруженную карту клиента.
* Клиенту нужны данные игры для поиска тайлов (`looks_like`, группы соединений): при подключении он грузит моды хоста, подставив временный `WORLD` в памяти как активный мир; при выходе — снова только core-данные.
* `get_window_dimensions( pos, size )` без окна путает его с `g->w_terrain` (у клиента пустым) и возвращает 0×0 — для области карты клиента заведено отдельное окно `w_map`.
* Крафт второго игрока: окно — копия экрана крафта хоста на клиенте (клиент грузит данные модов хоста и в текстовом режиме), а доступность, описание и поиск считает хост теми же функциями `crafting_gui.cpp` (наружу выведены обёртки `mp::craft_screen`). RC-NPC крафтит как аватар (`craft_activity_actor`, а не зональный `ACT_MULTIPLE_CRAFT`), компоненты выбирает без вопросов; при занятых руках кладёт заготовку рядом, оружие не бросает. Исправлен баг ядра: NPC не брал компоненты «частью из инвентаря, частью рядом».
* «Как у хоста» для экранов: клиент держит копию персонажа в своём аватаре (`npc::serialize` хоста → `avatar::deserialize`) и вызывает те же функции UI игры; где UI начал бы действовать, стоит хук, отправляющий выбор на хост. Подмена аватара на хосте (как `control_npc`) отвергнута: `item_location` и активности ссылаются на объект персонажа, и обмен данными их ломает.
* Клиент — «зеркало»: игровое состояние вокруг второго игрока копируется в обычные структуры игры клиента, и клиент рисует/открывает экраны тем же кодом, что хост. Выполняет действия только хост.
* Сообщение «игра запущена на порту…» у хоста — в логе, а не попапом: попап держит сеть, пока его не закроют.
* Хук RC-NPC ставится в начало `npc::move()`; пауза не может быть «выходом без траты ходов» — через 10 таких выходов `monmove()` вызывает `npc::reboot()` (NPC «падает в обморок»).
